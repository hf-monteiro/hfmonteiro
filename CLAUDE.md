# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Personal portfolio site (hfmonteiro.dev) built with Next.js 14 App Router, React 18, TypeScript and Tailwind CSS. Deployed to Cloudflare Pages as a **static export** (`output: "export"` in `next.config.js`, build output in `out/`).

## Commands

```bash
npm install
npm run dev     # local dev server
npm run build      # static export to out/
npm run typecheck  # tsc --noEmit (needs next-env.d.ts, generated by a build)
```

Don't run `npm run build` while `npm run dev` is running: both write to `.next/` and the dev server loses its CSS. Stop dev, `rm -rf .next`, then restart it after building.

There is no lint script and no test suite. Use `npm run build` to validate changes. TypeScript runs with `strict: false`.

## CI / Deployment

- **Deploy:** Cloudflare Pages' Git integration builds (`npm run build` → `out/`) and publishes every push on its own; build settings live in the Cloudflare dashboard, not the repo. Pushes to `main` go to production.
- **Checks:** `.github/workflows/ci.yml` runs on pushes and PRs to `main`: build, type-check, a lychee link check over `out/` (internal and external links, LinkedIn excluded), and Lighthouse CI (`lighthouserc.json`; SEO below 0.9 fails, other categories only warn). It does not deploy. Renaming a GitHub repo referenced from Labs or case studies breaks the link check.

## Architecture

### Static export constraints
Because the site is fully static, there are no server runtime features: no API routes, middleware, `headers()`/`cookies()`, or on-demand rendering. Dynamic routes (`[slug]`) must implement `generateStaticParams()`. Images are unoptimized. `app/sitemap.ts` and `app/robots.ts` are generated at build time.

### Bilingual routing (EN + PT-BR)
- English pages live in the route group `app/(en)/` and are served at the root (`/`, `/case-studies`, ...).
- Portuguese pages live in `app/pt-br/` and are served under `/pt-br/...`.
- Each language has its own `layout.tsx` that renders `Header`/`Footer` with copy from `lib/siteCopy.ts`.
- **Every route exists twice** (one `page.tsx` per language), but the markup is shared: each page file holds only its metadata and a typed `copy` object, and renders a view from `components/views/` (`HomeView`, `CaseStudyViews`, `LabsView`, `NotesViews`, `ResumeView`, `ContactView`) with `lang` and `copy`. Layout/UI changes go in the view; text changes go in both language files (the view's exported `*Copy` type keeps them in sync). New routes must also be added to `app/sitemap.ts` (maintained by hand for static routes).
- `components/LangSwitch.tsx` maps the current path to the other language by adding/removing the `/pt-br` prefix, so equivalent pages must share the same path segments and slugs across languages. Use `langBase(lang)` for in-app links.
- `lib/i18n.ts` defines the `Lang` type (`"en" | "pt-br"`) and helpers.

### Where content lives
- Structured, list/detail content is in `lib/` as `Record<Lang, T[]>` data keyed by language: case studies (`lib/caseStudies.ts`) and notes (`lib/notes.ts`), with getter functions (`getCaseStudies(lang)`, `getNote(lang, slug)`, ...). Slugs must match between the `en` and `pt-br` arrays.
- Page-specific copy (home, resume, labs, contact, list-page labels) is the `const copy` object in each language's page file.
- Nav/footer copy is in `lib/siteCopy.ts`.
- `public/resume.pdf` is the downloadable CV; the resume page content is maintained manually and should be kept in sync with it.

### Architecture diagrams
Case study detail pages render `components/ArchitectureDiagram.tsx`, which holds Mermaid `flowchart` definitions keyed by case-study slug (shared by both languages). `components/MermaidChart.tsx` is a client component that lazy-loads `mermaid` and renders with the palette from `lib/palette.js`. Adding a case study diagram means adding an entry keyed by its slug. Diagrams scale down to the container width (Mermaid's default `useMaxWidth`), so keep each one under ~1300px natural width or its text becomes unreadable: long `LR` chains should be split into stacked `subgraph`s with `direction LR` inside a top-level `flowchart TD` (a subgraph's `direction` is ignored if its inner nodes link outside it, so link subgraph-to-subgraph). On phones diagrams keep a 40rem minimum width and scroll horizontally.

### Social preview (Open Graph) images
`app/og/[image]/route.tsx` renders static PNGs at build time (`/og/site-<lang>.png` and `/og/<case-study-slug>-<lang>.png`) using `lib/ogImage.tsx`. Pages reference them with `ogImageUrl(lang, slug?)`: each language layout sets the site image as the default, but a page that defines its own `openGraph` replaces the layout's entirely, so it must include `images` itself. New case studies get an image automatically. Next 14.1's `opengraph-image.tsx` file convention is not used because it fails under `output: "export"` in dynamic routes and emits files without a `.png` extension.

### Design: production dashboard
The site is styled as a production-environment dashboard (Grafana/Datadog-like): a site-wide `StatusBar` under the header, monospace breadcrumbs (`PageHeader` `path`), and content in `Panel`s (bordered box with a mono uppercase header row). Case studies render as monitored "services" (`ServiceList`, `StatusBadges`), the home page has metric tiles, a career event log and a stack panel. **Everything shown must be real**: metrics come from the résumé, and the status bar's commit/build date come from `lib/buildInfo.ts` (Cloudflare `CF_PAGES_COMMIT_SHA`, GitHub `GITHUB_SHA`, else `git`). Don't add invented numbers, fake charts or live-looking counters. Status is never color-only: dots always sit next to a text label. Long-form reading (note bodies) stays unboxed at reading width. The résumé page derives its timeline chart, role tenure, `current` badge and certification status from the `period` / cert-year strings at build time (`ResumeView.tsx`); keep those strings in the `Mon YYYY - Mon YYYY` / `(YYYY–YYYY)` formats. A cert in its final validity year shows "expires YYYY", never "active", because only years are known. The Labs page is a Backstage-style catalog: each lab's language and last-push date come from one GitHub API call at build time (`lib/github.ts`, uses `GITHUB_TOKEN` if set); if it fails the page still builds and shows "—". `kind` and `legacy` in the labs copy are hand-set; `language` in the copy is only a fallback when GitHub reports none. Notes are a docs portal: list tiles, word counts, reading minutes (parsed from `readingTime`) and the note page's "on this page" TOC (anchors from section headings) are derived from `lib/notes.ts`. Dates display as ISO `YYYY-MM-DD` site-wide. Contact is a service-desk view: the request form (`ContactRequest`) has no backend and only builds a pre-filled `mailto:` link; the local-time tile is a client-side clock for America/Sao_Paulo. Don't add availability or response-time claims without the owner's confirmation.

### Styling and themes
Tailwind only, with dark and light themes. Colors are defined once in `lib/palette.js` (`themes.dark` / `themes.light`) and exposed as role-named Tailwind classes that read CSS variables: `night-*` (neutral scale), `accent` / `accent-hover` (interactive: links, bullets, focus), `highlight` (metric values), `success` (health/status, outcome bullets). The `night` scale is semantic, not literal: 950 is always the page background and 100 the strongest text, so it is inverted in light mode. Never use `white`/`black`, Tailwind's default grey scales, or raw hex in components, or they won't switch themes (use `night-50` for "max contrast").
- `app/layout.tsx` emits the CSS variables (`:root` = dark, `[data-theme="light"]`) and an inline script that sets `data-theme` on `<html>` before first paint (saved `localStorage.theme`, else the OS preference). `ThemeToggle` (header) flips it and saves the choice.
- Mermaid reads the live CSS variables and re-renders when `data-theme` changes; the OG images always use `themes.dark`. The logo is white artwork, inverted in light mode via `.logo-invert`.
- Use `night-400` or lighter for readable small text (`night-500` fails contrast). Light mode has its own darker accent/success shades for contrast; check both themes when adding colors.
- Grid children that contain wide content (diagrams) need `min-w-0` (`Panel` has it) or they overflow on phones. Imports use the `@/` alias for the repo root.
